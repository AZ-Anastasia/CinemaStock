## Строки из CinemaStock.Shared

### Общее и маршруты

Чтобы каждый раз не искать маршруты и другие строки, они были вынесены в отдельные файлы в `CinemaStock.Shared`:
- ***ConstStrings.cs*** - строки по типу **стандартный формат даты**, **путь до картинки для киноконтента по умолчанию**.
- ***Resources/...*** - локализация на разные языки.
- ***Routes/ApiRoutes.cs*** - маршруты до эндпоинтов для выполнения HTTP-методов. Так как с клиента до сервера запрос проходит путь:
```
CinemaStock.Client/Services/Clients/[Выбранный_клиент].cs -> 
CinemaStock.API/Services/[Выбранный_сервис].cs ->
CinemaStock.API/Controllers/[Выбранный_контроллер].cs
```
, то менять маршруты было бы проблематично, т.к. путь до эндпоинта (например, до GET на получение списка киноконтента) указывается:
- и в `CinemaStock.Client/Services/Clients/[Выбранный_клиент].cs`
```cs
var url = $"{ApiRoutes.Admin.GetCinemaContent}?page={pageNumber}&pageSize={pageSize}";
```

- и в `CinemaStock.API/Controllers/[Выбранный_контроллер].cs`
```cs
[HttpGet(ApiRoutes.Admin.GetCinemaEndpoint)]
```

### Роли и доступ к HTTP-методам по ролям

Для ограничения доступа к HTTP-методам используется атрибут доступа по роли для авторизованных пользователей:
```cs
[Authorize(Roles = "Admin")]
```

Так как задавать роль в программе нельзя (нужен ручной выбор пользователя, которому нужно предоставить права в БД), используется следующий ***алгоритм ручного задания роли***:
1. Запустить контейнер Docker с PostgreSQL в корне `CinemaStock.API`:
```bash
docker compose up -d
```
2. Выполнить команду для запуска терминала для SQL
```bash
docker exec -it postgres-cinemastock psql -U [Имя_пользователя] -d [Название_БД]
```
*Примечание*: подробно расписано откуда брать данные для команды в файле `README.md`.

3. Когда терминал открыл строку для SQL, просматриваем таблицу `AspNetRoles`
```sql
SELECT * FROM "AspNetRoles";
```
4. Вставляем запись с ролью (т.к. в программе используется `Admin`, то и название будет такое же. В качестве `Id` можно взять любое незанятое число):
```sql
INSERT INTO "AspNetRoles" ("Id", "Name") VALUES ('[Любое_незанятое_число]', 'Admin');

Вывод:
INSERT 0 1
```
5. Просматриваем пользователей и находим нужного с нужным ID:
```sql
SELECT "Id", "UserName" FROM "AspNetUsers";

Вывод:
UserId | RoleId 
--------+--------
[Id_Пользователя] | [Id_Роли]
```
6. Вставляем запись в таблицу `AspNetUserRoles`:
```sql
INSERT INTO "AspNetUserRoles" ("UserId", "RoleId") VALUES ("[Id_из_AspNetUsers]", "[Id_из_AspNetRoles]");
```

### Про страницы .razor

Для отображения UI используются .razor страницы. В страницах есть переиспользуемые компоненты, которые выделены в отдельные .razor-файлы (например, `EmptyState.razor`)

`EmptyState.razor` - компонент для отображения информации о том, что:
- запрашиваемая страница не существует
- в БД сейчас нет данных
- и т.д.

`ErrorBlock.razor` - небольшой контейнер для отображения сообщений об ошибках (например, при регистрации или входе).

Шапка выведена отдельно в `SiteHeader.razor`. Иконка сайта без картинок - `<svg>`. Отображение шапки встроено в `MainLayout.razor` для переиспользования в других страницах.

### Typed Clients, Credentials and Cookies

1. Зачем нужны Typed Clients (Типизированные клиенты)

Соблюдение SRP. Страница Blazor отвечает только за UI, а клиент (`..Client.cs`) - за запросы к серверу (удобный вызов через методы без необходимости прописывать всю структуру вызова в коде страницы в `@code` или `.razor.cs`)

Клиенты как Gateway к API. Весь повторяющийся код (десериализация, обработка ошибок, обработка статус-кодов) вынесен в `ApiHttpClient`.

2. Зачем связаны `Credentials` и `Cookies`

По соображениям безопасности браузер блокирует передачу кук авторизации при HTTP-запросах к сторонним API (даже между разными портами на `localhost`). Чтобы бэкенд понимал, какой пользователь делает запрос, куки нужно передавать принудительно. Как это решается:

Выстроена цепочка хэндлеров (клиентский Middleware):
```
HttpClient->CredentialsHandler->CookieHandler->Сеть
```

**Результат**: `CredentialsHandler` автоматически выставляет флаг `Include` для браузерных кук. Не нужно писать эту настройку вручную внутри каждого метода отправки данных.

3. Для чего создан Класс Расширения (`ClientRegistrationExtensions`)

Если регистрировать каждого доменного клиента вручную в `Program.cs` на клиенте, настраивая для него базовый URL и цепочку хэндлеров, главный файл приложения раздуется на сотни строк одинакового кода.

**Как это работает**: Метод `AddCinemaStockClient<T>` инкапсулирует всю низкоуровневую сборку `HttpClient`. В `Program.cs` регистрация нового клиента теперь занимает ровно одну декларативную строчку. \
**Архитектурный плюс**: Каждый клиент получает свой изолированный экземпляр `HttpClient`. Они работают независимо и не блокируют друг друга при параллельных запросах к базе данных. При этом сохраняется полный контроль над DI-контейнером (всегда видно, какой клиент подключен, а какой можно временно отключить).

## Про вставку изображения при работе с киноконтентом (добавление, редактирование)

### Архитектурное руководство: Реализация Clipboard Paste (Ctrl+V) и Drag-and-Drop для изображений в Blazor WebAssembly

#### 1. В чем заключалась проблема (Root Cause Analysis)

Изначальный подход основывался на классической веб-парадигме: перехватить файл в JavaScript, программно внедрить его в `<input type="file">` и сгенерировать событие `change` в надежде, что стандартный компонент Blazor `<InputFile>` подхватит его. 

Этот подход **сломался о внутреннее устройство Blazor** по двум причинам:
1. **Нарушение виртуального DOM (DOM Mutation):** Компонент `<InputFile>` в Blazor — это не просто HTML-тег, а сложная инфраструктурная C#-структура. Она синхронизирует состояние файлов через жестко регламентированный внутренний JS-мост (`Microsoft.AspNetCore.Components.Forms`). Когда кастомный JS-код насильно перезаписал свойство инпута `.files`, Blazor расценил это как стороннее несанкционированное вмешательство в DOM и заблокировал вызов C#-метода `HandleFileSelected`.
2. **Маршалинг и потеря контекста Blob URL:** Попытка гонять `ElementReference` в JS-функцию `createPreviewUrl` обратно после мутации инпута приводила к асинхронным гонкам данных (Race Conditions). Файл в Clipboard существовал мгновение, и Blazor терял ссылку на него еще до того, как успевал сгенерировать `blob:http://...` ссылку.
3. **Падение `ArgumentOutOfRangeException`:** При вставке файлов браузер генерировал строку DataURL. В некоторых сценариях (особенно при обработке сырых бинарных данных из буфера) мета-префикс `data:image/...;base64,` мог отсутствовать или формироваться некорректно. Использование жесткого `.Substring(base64Data.IndexOf(",") + 1)` без предварительной проверки возвращало `-1`, что приводило к критическому сбою потока.

---

#### 2. Как работает новое архитектурное решение

Новая архитектура полностью исключает `<InputFile>` из процесса обработки `Ctrl+V` и `Drag-and-Drop`. Вместо этого используется **прямой изолированный канал связи через `JS Interop` (DotNetObjectReference)**.

Пошаговый жизненный цикл данных:
1. **Глобальный перехват:** JS-код слушает системное прерывание `window.addEventListener('paste', ...)`.
2. **Извлечение:** Из `e.clipboardData.files` берется первый файл (картинка).
3. **Конвертация в поток данных:** С помощью встроенного в браузер объекта `FileReader` файл считывается асинхронно методом `readAsDataURL(file)`. Это преобразует бинарный файл в текстовую строку Base64.
4. **Прямой мост (C# Invoke):** Через специальный хэндлер `invokeMethodAsync` строка Base64 и имя файла поступают напрямую в недра C#-кода компонента, минуя UI-элементы.
5. **Безопасный парсинг:** C# метод `HandleExternalFile` проверяет строку, безопасно отсекает заголовки (если они есть), валидирует размер через длину массива байт и обновляет `previewUrl` для мгновенного рендеринга.

---

#### 3. Спецификация API взаимодействия (Контракт)

### JavaScript (Отправитель)
```javascript
// Вызов C#-метода по его [JSInvokable] имени
inputElement.invokeMethodAsync('HandleExternalFile', event.target.result, file.name)
```
*   Параметр 1: Уникальный строковый идентификатор метода в Blazor.
*   Параметр 2 (`string`): Полная DataURL строка из `FileReader`.
*   Параметр 3 (`string`): Имя файла (например, `image.png` или `blob` при системном скриншоте).

---

#### 4. Преимущества данного подхода (Плюсы для продакшена)

1.  **Стабильность:** 100% иммунитет к обновлениям версий Blazor Forms и структуре внутренних UI-компонентов.
2.  **Производительность и Утечки памяти:** Старый метод генерировал тяжелые ссылки `blob:http...`, которые требовали ручной очистки памяти через `URL.revokeObjectURL`. Использование Base64 строки напрямую в теге `<img src="@previewUrl" />` освобождает память автоматически, как только компонент уничтожается.
3.  **Кроссбраузерность:** Метод FileReader одинаково стабильно работает во всех современных браузерах (Chromium, Firefox, Safari, WebKit под Linux).
