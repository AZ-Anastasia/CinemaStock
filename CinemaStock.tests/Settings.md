# python.ini - конфигурационный файл фреймворка playwright
Аналог `appsettings.json` или `launchSettings.json`. Задает глобальные параметры для тестового проекта. \
`.ini` - классический текстовый формат конфигурации ("ключ=значение").

`[pytest]` - заголовок секции. Все, что написано ниже - глобальные настройки. Аналог `.runsettings` от `Playwright` или .NET `"Logging": {}` в JSON и прочих настроек по типу `"DefaultConnectionStrings"`.

`addopts` - add options - при вводе команды в терминал будет автоматически подставлять строку с флагами.

`testpaths` - путь к папке с тестами. В проекте тесты находятся в `tests`.

# conftest.py - создание общих фикстур. Подгрузка данных из файлов конфигураций

## @pytest.fixture(scope="session")
|Значение scope|Как работает|Для чего используется|
|-|-|-|
|function (по умолчанию)|Код фикстуры запускается заново для каждого отдельного теста|Очистить БД перед тестом, открыть чистую вкладку браузера|
|class|Выполняется один раз для группы тестов, объединенных в класс|Группировка тестов со схожими тяжелыми настройками|
|module|Выполняется один раз для одного файла с тестами (модуля)|Подготовить специфичные данные только для тестов авторизации|
|session|Выполняется один раз на весь запуск проекта|Чтение глобальных конфигов (.env), создание пула соединений, авторизация мастер-пользователя|

## API region

Для приведения к модели ответа используется `.parse_to`.

Чтобы получать ответ в удобном виде используются обертки в `httpx_client()`, однако использовать их - не лучшее решение, потому что они выводят все данные в открытом виде в консоль `python` при получении ответа.

# Тестовые данные
Чтобы не хардкодить данные в проекте, создана папка `./tests/data`, в которой находятся JSON-файлы с данными. Помещать данные в `.env` - `.env` не загружается в `Git`, потому что хранит настройки, а здесь речь о тестовых данных.

Считывание файла происходит 1 раз с помощью `@pytest.fixture(scope="session")`.

Чтобы не писать в `login_data.json` в открытую пароль, используется перекрывающее значение `"VALID_PASSWORD"`: при совпадении с этой строкой она заменяется строкой из файла `.env`. Для почты и логина используется тот же принцип.

Так как в проекте сообщения об ошибках подтягиваются через ресурсные файлы, была написана функция парсинга XML-файла `load_resx_strings()`. В данной функции учитывается язык системы для сопоставления языка сообщения об ошибке. Сообщение об ошибке для проверки указывается в файле с тестовыми данными (указывается ключ в поле `resx_error_key`). Если ошибка встроенная (например, из БД), то можно задать ее в тестовых данных в виде фразы.
